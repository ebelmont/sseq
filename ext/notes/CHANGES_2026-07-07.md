## 1. Sweep optimization (ehp-core/src/interpage.rs) — the big one

**Before:** `sweep <r>` ran 2×U independent trials; each trial re-turned
thousands of degrees (`get_tb`) from scratch, deep-cloned the target SATPage,
rebuilt by_n/by_ns/stale-block indices by scanning all page keys/blocks, and
deep-cloned/dropped all TurnedBidegrees. ~85% of time was allocator churn.
t=50/MAX_R=6 sweep: **749.6s**. t=100 extrapolated to days.

**After:** **9.9s** at t=50 (~75×); t=70/MAX_R=7 = 2492 trials in minutes.
[PARITY] [ADVERSARIAL] Components (each separable):

a. **Filter reorder** — product-candidate filters (max_s / unit-degree /
   recomputable / shifted-present / polygon) run BEFORE the needed-turned-
   degree collection (`candidates.retain(..)` in `build_overlay_page`), so
   rejected triples never cost a page turn. This was the single biggest win.
   Accepted math delta: trials no longer *incidentally* detect d∘d≠0 at
   degrees only rejected candidates needed — detection now matches the
   canonical triple enumeration exactly (reviewed; the parity runs at t=50
   and the t=70 forced value were identical).
   *Revert:* move the retained predicates back into the product apply-loop
   after `tb_at` lookups and rebuild `needed` from ALL candidates.

b. **`TbCache`** — get_tb results for the stock first page + base result,
   precomputed in parallel at sweep start, then read lock-free. Trials
   consult it only on the FIRST page step and only at degrees whose
   rep(t)/rep(t_in) is not in the trial's dirty set (degrees of assumed +
   learned vars — provably the only places the trial's result differs;
   see the invariant writeup in SESSION_HANDOFF §July 7). Do NOT reintroduce
   a lazy RwLock version — it was 3× slower under rayon contention.
   *Revert:* pass `None` instead of `Some(&cache)` in `trial_error_sweep`
   (one line) — trials then always compute fresh, exactly the old semantics.

c. **`SweepCache` / `PageIndex` / `SourceIndex`** — per-sweep precomputed
   stock-page indices (partner lists by n / n+s; keys, naturality squares,
   product blocks inverted by stable rep), consumed with per-trial
   added/removed dimension deltas. GOTCHA: partner lookups are ITERATOR
   CHAINS on purpose; building filtered Vec copies per lookup was a 2.7×
   regression at t=70 (invisible at t=50).
   *Revert:* same one-liner as (b) — with no cache, `build_overlay_page`
   builds a local PageIndex per call (slower for bulk try_diffs but same
   results).

d. **Arc'd turned data** — `LocalTurn::tbs` and the overlay tbs maps hold
   `Arc<TurnedBidegree>` (was owned values; cloning/dropping them was ~20%
   of sweep time). *Revert:* mechanical de-Arc; no semantic content.

e. **`try_diffs_with_cache`** — public wrapper; plain `try_diffs` unchanged
   behavior (cache=None). REPL `try` uses the uncached path.

## 3. build_pairs removal (io.rs, pageturning.rs, ehp-server/src/lib.rs, ehp-cli/src/main.rs)

**Before:** `SATPage.pairs` (degree → partner-degree list) was built on E2
load AND after every page turn — ~13% of startup CPU, single-threaded.
**After:** all `build_pairs()` calls removed; field kept + documented as
unpopulated. [PARITY]

**Evidence it was safe:** `grep -rn '\.pairs'` across all crates — the ONLY
reader is `diag_clone_cost.rs` (a size-measuring diagnostic). The Leibniz
enumeration in `build_constraint_system` iterates its own s/f/n loops with
data-driven bounds (`max_data_n`) and NEVER consulted `page.pairs`; removing
it changed no constraint. Parity at t=50 byte-identical post-removal.

**USER CONCERN (recorded):** the intuition "pairs makes Leibniz cheaper by
restricting which pairs are checked" describes what pairs SHOULD do, not
what the Rust code ever did. FUTURE WORK (do not revert; implement instead):
gate the Leibniz pair enumeration with a precomputed nonzero-product index
(revive `pairs` as an actual consumer-driven index) — today's diagnostics
show ~95k candidate pairs scanned per variable neighborhood with the vast
majority guard-rejected; a product-support index could cut constraint
generation dramatically. If implemented, benchmark at t≥70 (see §10).

*Revert (if ever needed):* re-add `page.build_pairs()` at io.rs (after
load), pageturning.rs `build_page_from_turned` (before `next`), lib.rs
(both load sites), ehp-cli (both sites). Costs ~13% startup for no current
consumer.

## 11. E4 UNSAT diagnosis (experimentally confirmed A/B matrix at t=80)

| relax (§8a) | outside diffs | result |
|---|---|---|
| ON (default) | ON | **UNSAT at E4** (user's config; 1275s total) |
| OFF (`EHP_RELAX_TARGET_EXCLUDE=0`) | ON | all pages SAT (654s) |
| ON | OFF | all pages SAT (744s) |

Mechanism (4-agent audit, every claim adversarially verified against code +
`~/EHP_SAT/ehp_sat` reference, then confirmed by the matrix above):

- Outside rows for r≥3 pin `[row,col]` entries that are ONLY meaningful in
  the basis of the pipeline that recorded them. Rust's E3/E4 bases differ
  from the recording (Python) pipeline's at any degree downstream of a
  partially-determined differential (partial-matrix turning vs whole-matrix
  zeroing; recording runs also carried lh0 constraints).
- Python only asserts a row if its variable already exists (drops rows at
  excluded degrees and inside a per-page cutoff margin, max_t decrementing
  per turn minus r−1). Rust `add_known_diff_vars` force-creates blocks at ANY
  degree with nonzero dims and pins the value — deliberate for interactive
  user asserts (made against the CURRENT chart, basis-consistent by
  construction), wrong for bulk-imported rows.
- §8a relax (default ON) is the enabling change for UNSAT: pre-relax, a
  wrong-basis pin at an excluded degree was an isolated unit clause (can't
  contradict anything); relax lets those variables into Leibniz rows — one
  mis-indexed pin ⇒ page UNSAT.
- t=80 vs t=50: only ~12 interior E4 rows load at t≤50 (bases coincide,
  SAT); at t=80 another ~38 d4 + ~52 d3 rows in the 50<s+f≤80 band land
  exactly where target-only exclusions are dense (stable high-stem region).

## 13. Startup performance (the §10 lesson applied: profile first)

`sample` on the live t=80 startup showed single-threaded
`build_constraint_system` with ~65% in `SATPage::map_matrix` → posix_memalign
(zero/identity DEFAULT matrices materialized per Leibniz/naturality lookup),

identical per-page determined counts at t=50 and t=80.

a. **`SATPage::map_matrix_ref`** (page.rs) — borrowed/virtual enum
   (`Stored(&Matrix)` / `Identity(n)` / `Zero(src,tgt)`) with
   `to_matrix()`, `to_matrix_transposed()`, `apply_vec()`; `map_matrix`
   delegates, callers in constraints.rs (Leibniz e_matrix, e_mat_at_d,
   naturality phi_source/phi_target) no longer materialize defaults.
   *Revert:* switch call sites back to `page.map_matrix(...)`.
b. **Ytilde all-zero early-out** (constraints.rs, rhs1 + rhs2) — if all
   `ytil_cols` are zero the result equals the mat_is_zero branch; skip the
   matrix build. Strictly below the fail-fast guards (per the §4/§10 lesson).
   *Revert:* delete the two `if ... all is_zero` early branches.
c. **Product-support pair fast path** (constraints.rs + products.rs
   `has_block`) — a Leibniz pair consults only blocks (deg1, e_deg2),
   (deg1, d(E deg2)), (d_deg1, deg2); all three absent ⇒ every term is zero
   ⇒ `equals_rel` emits nothing and no `skip()` path is reachable ⇒ pair is
   a no-op: return early after the exclusion bookkeeping (recording
   unchanged). This is the minimal form of §3's FUTURE-WORK product-support
   index. *Revert:* delete the has_block early return.
d. **CSV load skip** (io.rs) — product rows with a factor outside the loaded
   s+f window (dim 0) can never be consulted; skip before the result-string
   alloc and table insert (2.33M → 0.77M inserts at t=50; the "Loaded N
   products" count now reflects kept rows). Same skip-before-string-work in
   load_map_csv. Load TIME is dominated elsewhere (fp Matrix::new per block;
   pre-existing, from the this-week binary→CSV default switch) — future
   work, needs quiet-machine benchmarking. *Revert:* move the dim checks
   back below the parse.

## 16. d²=0 one-leg linearization (2026-07-08; kill-switch `EHP_D2_LINEAR=0`)

Tier 1 of the nonlinear-constraint plan (Tier 2 — a CryptoMiniSat backbone
sweep for both-legs-unknown quadratics — is designed but not built).

d∘d = 0 on a page is quadratic in the differential entries, but whenever one
leg of a composable pair A → B → C is determined it is linear in the other:
a determined column i of d(A) with support S forces `Σ_{j∈S} d(B)[k,j] = 0`
for every k, and a determined row k of d(B) with support T forces
`Σ_{j∈T} d(A)[j,i] = 0` for every i.

- `constraints::make_d2_linear_rows(page, result)` — emits those rows from
  the current solve; only at degrees where A, B, C are all unexcluded,
  in-polygon, nonzero-dim (uncertainty contract); stable copies skipped
  (they share the rep's variables).
- `solver::solve_with_d2(page, system)` — plain solve, then fixpoint: fresh
  rows folded in via `interpage::update_sat_result` (kernel augmentation, no
  re-solve; per-pass row dedup; ≤16 passes). UNSAT here is a genuine
  contradiction (every row is a true consequence of d²=0 + clean determined
  values) and is reported as such.
- Wired into: REPL startup solve, cascade re-solve, `solve_and_export`
  (regen), and diag_startup. NOT wired into the interpage trial path (sweeps
  already exploit d² by trial + propagation; the trial path stays
  byte-identical on the `diag_sweep_verify` harness — verified) nor the
  batch-bisect probe (it should explain base-system inconsistencies only).

Verified at t=50 (outside diffs, strict defaults): +1 determined entry on
E_2 (5468 → 5469), all pages SAT, no measurable solve cost. t=80 result
recorded when the run lands.

## 17. Experimental dense solver (`EHP_SOLVER=dense` | `verify`; default unchanged)

The constraint rows were always dense fp bit-vectors, but the ELIMINATION
was hand-rolled in gf2.rs during the Python-parity port (`mat_echelon_form`
per-column pivot searches; consistency/kernel scans reading single bits —
order rows×cols `entry()` calls, ~10^10 at t=80). fp's own M4RI
`Matrix::row_reduce` (the optimized kernel the Adams resolutions use) was
never wired up — the solve was 0.2s at t≤50 so nobody noticed until this
week's fixes exposed the 75–115s/page cost at t=80.

`solver::solve_dense`: ONE augmented `fp::Matrix [A | b]`, M4RI row_reduce,
then solution/kernel/unknowns read off the RREF with limb-level scans. RREF
is canonical ⇒ output provably identical to the classic solver.
- `EHP_SOLVER=dense` uses it; `EHP_SOLVER=verify` runs BOTH, byte-compares
  offset/kernel/unknown, logs both timings, warns loudly on mismatch and
  returns the classic result; unset = classic path, bit-for-bit as before.
- Evidence: `dense_matches_classic` unit test (solve/kernel/inconsistency);
  full t=50 chain under verify — zero mismatches, all pages SAT.
- t=80 timing comparison: PENDING (run `EHP_SOLVER=verify` at t=80 and
  record the per-page "classic X.XXs, dense Y.YYs" lines here).
- Not applicable to the tiny per-degree eliminations (page-turn quotients,
  Ytilde ranks): M4RI wins on one big matrix, not many small ones.
