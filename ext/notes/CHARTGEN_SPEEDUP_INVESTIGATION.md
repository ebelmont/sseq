# Chart-generation speedup — investigation kickoff (2026-07-31)

Goal: radically reduce chart generation time. It is by far the longest part of
the pipeline at scale (t=100), yet it is pure visual rendering — none of it is
the mathematics. This note seeds a dedicated investigation session.

## Current architecture (what exists today)

- Charts are self-contained HTML generated by the SHARED python SeqSee repo
  (`~/seqsee/seqsee_new/`): `jsonmaker.py` (CSV → JSON) → `main.py` (JSON →
  SVG/HTML via jinja template `template.html.jinja`), one HTML per
  sphere/stem/fiber/page, plus split-screen map views.
- Already optimized (don't re-do): batched generation (`ehp_batch.py` — one
  python process renders a whole chunk; one chunk per CPU in parallel), venv
  python resolved once, stale-chart cleanup, warm-start chart ARCHIVING
  (APFS copy-on-write clone into the cache dir — warm starts restore in <1s
  instead of regenerating), snapshot chart clones, and mutation-time regen
  limited to affected charts (`regen_affected_charts`, now including
  determination/exclusion-change degrees).
- Chart count multipliers per session: spheres × pages + stems × pages +
  fibers × pages + PRE-GENERATED split-screen map views for every map ×
  sphere × page (`EHP_MAPVIEWS`; `mapview all`). The charts dir is multi-GB.
- Every HTML embeds: all theme CSS blocks, KaTeX, pan/zoom JS, the full SVG,
  plus injected scripts (CLICK_SCRIPT ~800 lines, fiber script, view menu).
  Charts are file:// — the historical reason everything is inlined.

## Where the time probably goes (hypotheses to PROFILE FIRST, not assume)

1. **Sheer chart count** — the map-view pre-generation multiplier is likely
   the single biggest factor (maps × spheres × pages ≫ spheres × pages).
2. **Per-chart python/render cost** — jsonmaker+jinja per chart; python
   startup is already amortized by batching, so measure render vs IO split.
3. **Disk IO / HTML size** — multi-GB of mostly-duplicated bytes (themes,
   KaTeX, JS identical in every file). Writing is O(bytes), and the
   injectors (markers, view menu, hidden overlay) re-read+re-write whole
   files repeatedly.
4. **Injection passes** — several full read/replace/write sweeps over every
   chart at startup (view menu, fiber scripts, map info, DIFFDATA/CLASSDIMS,
   PROPDATA, HIDDENDATA). Each is O(total bytes on disk).

## Candidate directions (roughly by expected payoff / risk)

- **A. Generate on demand, not up front.** Only the charts the user actually
  opens need to exist. WASD/e-h-p navigation already handles missing files
  (copies a command instead of navigating). Options: (i) lazy generation via
  a REPL `open <chart>` + click-driven flow; (ii) a tiny background generator
  thread that fills in the rest after startup (startup shows the first charts
  immediately, the tail generates while the user works). Biggest win if
  map views move to on-demand (they already have the `mapview` command path).
- **B. Shared assets instead of inlining.** file:// allows RELATIVE
  `<script src>` / `<link href>` within the same directory — the
  self-containment constraint is per-directory, not per-file. Moving KaTeX,
  theme CSS, pan/zoom, and the big injected scripts into shared files in
  `output/charts/` could cut per-chart bytes (and injector rewrite cost) by
  an order of magnitude. CAVEAT: the injected-data markers (DIFFDATA etc.)
  are per-chart and must stay in the HTML; the cache/snapshot archiving and
  "open index.html directly" self-containment must keep working (assets live
  in the same archived dir, so they should). Verify browser behavior for
  file:// relative loads on the user's browser first.
- **C. Rust-native rendering.** Port jsonmaker+main.py layout/SVG emission
  to Rust (ehp-server already computes most inputs; seqsee.rs writes the
  CSVs those scripts re-parse — a Rust renderer would skip CSV→JSON→SVG
  entirely and drop the python dependency). Highest effort; huge payoff;
  risks divergence from the shared SeqSee repo used by other workflows —
  needs the user's buy-in on forking the renderer.
- **D. Injection consolidation.** One read → apply ALL injections → one
  write per chart (today each injector does its own pass). Cheap, bounded
  win; helps every startup and mutation.
- **E. Don't regenerate what didn't change.** Mutation-time regen now keys
  on affected degrees; startup regeneration after config changes could diff
  at chart granularity (per-sphere state stamp instead of one global stamp).

## Measurement plan (do this before choosing)

1. Instrument `ehp_batch.py` chunks: per-chart wall time split into
   jsonmaker / render / write (a `time.perf_counter` triple per chart,
   printed per chunk) — one run at the user's t=100 config.
2. Count + size: `find output/charts -name '*.html' | wc -l`, `du -sh`,
   broken down by sphere/stem/fiber/map-view prefix.
3. Time the injector passes separately (they're Rust-side; wrap with
   Instant prints behind a debug env flag).
4. Compare against the archived-restore path (<1s) to set the target:
   "generation should approach clone speed for unchanged charts".

## Constraints to respect

- Charts must remain openable directly from disk (file://, no server) —
  that's the architecture, per CLAUDE.md.
- The SeqSee repo is SHARED with other users/workflows — edits there must be
  surgical; a Rust renderer would be a fork decision for the user.
- Injected-JS changes require chart regen + hard reload (existing gotcha).
- Warm-cache chart archiving and snapshots must keep working unchanged.

## FIRST MEASUREMENTS (t=25, EHP_TIMING=1, 2026-07-31) — the smoking gun

Instrumentation is IN (see "Instrumentation" below). A 125-chart mutation
regen at t=25 breaks down as (CPU-side sums across parallel chunks):

| mode   | charts | jsonmaker (CSV→JSON) | render+write (JSON→HTML) | ratio |
|--------|--------|----------------------|--------------------------|-------|
| fiber  | 66     | 96.5s                | 3.3s                     | 29:1  |
| sphere | 43     | 24.1s                | 1.7s                     | 14:1  |
| stem   | 16     | 12.8s                | 0.6s                     | 21:1  |

**≈95% of chart-generation CPU is `jsonmaker.process_csv` re-parsing the
SAME page CSV once per chart.** Per chart: json≈0.6–1.5s, render≈0.04s.
The CSV grows with max_t, so at t=100 the ratio is likely worse.

→ Top candidate fix (likely 10–20×, python-only, no Rust port needed):
  parse each CSV ONCE per batch chunk and reuse the parsed rows across all
  items in `run_slices` (jsonmaker-level cache keyed on csv_path, or a
  `process_csv` variant taking pre-parsed rows). All items in a chunk share
  one csv_path already (per-page), so a single-entry cache suffices.
  The Rust renderer (option C) is probably UNNECESSARY if this lands —
  render+write is ~0.05s/chart.

### FIX LANDED (2026-07-31, vendored ext/seqsee/jsonmaker.py)

Implemented: (1) `_load_csv_cached` — (path, mtime)-keyed DataFrame cache for
every `pd.read_csv` site; (2) `_rows(df)` — list-of-dicts cached in
`df.attrs`, replacing all `iterrows()` sites (dict rows keep `row[key]` /
`.get` / KeyError semantics); (3) cached `load_schema` (NB: must call via the
`_seqsee_main` module alias — this file's own `def main()` shadows the `main`
module at call time); (4) `jsonschema.validate` now opt-in via
`SEQSEE_VALIDATE=1`; (5) `_fiber_nulldif_rows` — per-page cache of parsed
nulldif rows, so fiber charts stop re-reading every sibling CSV each.
`get_differential_info`'s O(n²) scan turned out to be dead code (never
called) — left as-is.

Verified: full t=25 corpus (540 HTML+JSON files) regenerated BYTE-IDENTICAL
to the pre-change baseline; mutation-regen smoke clean. Measured at t=25:
jsonmaker CPU fiber 96.5s→7.0s (14×), sphere 24.1s→2.7s (9×), stem
12.8s→1.3s (10×); 125-chart mutation regen wall 31s→12s. At t=100 the win is
larger (parse was 11–13s PER CHART there; it is now once per chunk).

Still open for the investigation session: render-side wins (skip the
JSON-file round-trip via a dict-accepting process_json; swap compact_json
Formatter for stdlib json), on-demand map views, shared assets. Re-profile
at t=100 first — jsonmaker and render are now the same order.

## Instrumentation (already implemented, 2026-07-31)

- `ext/seqsee/ehp_batch.py` (the VENDORED runtime copy — the external
  `~/seqsee/seqsee_new` checkout was NOT touched and is older/missing fiber
  mode): every chunk prints `TIMESUM <mode> items= json= render= bytes=` on
  stdout (protocol-safe: unknown prefixes are ignored by the Rust parser);
  with EHP_TIMING set, per-item `TIME <mode> <id> ...` lines too.
- ehp_chart.rs: `parse_batch_report` aggregates TIMESUM into a global;
  `print_chart_timing(context)` reports per-mode after startup generation,
  startup mapviews, mutation regens, and the `regen` command;
  `timed_phase(...)` stopwatches the injection passes (view menu, fiber/stem
  scripts, DIFFDATA overlays). All output only when `EHP_TIMING=1`
  (aggregation itself is always-on and free); charts byte-identical either
  way. Injection passes at t=25: ~0.1s (not a factor at this scale — re-check
  at t=100 where the charts dir is multi-GB).

## Known timings (this session, small scale)

- t=25, fiberviews+mapviews OFF: 4 pages × ~23 sphere charts + stems
  generated in roughly a minute total on first startup; archived restore of
  236 charts takes 0.14s (the ceiling to aim for).
- Mutation-time regen: 59 affected charts ≈ 15s (≈ 0.25s/chart).
- At t=100 the user reports chart generation dominates the whole pipeline.

## ROUND-TRIP SKIP LANDED + on-demand map-view plan (2026-08-01)

### 1. JSON round-trip skip (landed, vendored ext/seqsee/ only)

`main.py process_json` gained an optional `data=` kwarg: when passed an
already-parsed input dict it skips the `.json` re-read AND the unconditional
`jsonschema.validate` (opt back in with SEQSEE_VALIDATE=1, matching
jsonmaker's policy; the file path keeps unconditional validation for external
callers). `ehp_batch.py run_slices` now feeds the dict returned by
`jsonmaker.process_csv` straight into `process_json` (capability-probed via
`inspect.signature`, so the script still runs against an older main.py).

The `.json` files ARE still written, byte-identically — they have real
consumers: `annotate_json_with_jmap` in ehp_chart.rs reads `S{n}_E{r}.json`
to build the `map_*_src.json` inputs, and `generate_sidebyside_html` reads
both src and tgt JSONs from disk. Only the same-process re-read is skipped.
Mutation-in-place is safe: `process_csv` dumps to disk BEFORE returning the
dict, and builds a fresh dict per chart (the shared `_rows(df)` cache is
read-only in the extraction code). Float/typedata fidelity of the skipped
round-trip was verified (compact_json preserves 0.0-vs-0, full float repr).

Verified: full t=25 corpus (mapviews+fiberviews ON), 808 files (404 HTML +
403 JSON + index) — `diff -r` baseline vs post-change: byte-identical.
Controlled single-process benchmark (26 sphere charts, E2 CSV, warm caches):
render 3.93s -> 2.19s (~1.8x; the removed work is json.load + validate,
which scale with JSON size, so the win grows at t=100). Startup TIMESUM at
t=25 (cpu-side sums, noisy across parallel chunks): render
sphere 5.0->3.4s, stem 4.0->3.7s, fiber 5.8->5.5s.

### 2. compact_json -> stdlib json: NO (deliberate)

compact_json's output is a table-aligned format: padded keys
(`"S5_0_0" : `), right-aligned numbers (`"x":  0`), trailing spaces after
line-end commas, and length-budget object/array inlining. No
`json.dumps(separators=..., indent=...)` combination reproduces those bytes,
and the `.json` bytes are consumed downstream (jmap annotation, sidebyside
inputs) and archived, so they must stay stable. Kept; comment at the
`Formatter()` site in jsonmaker.py. (If the dump itself ever shows up in a
profile, the option is a hand-rolled byte-identical formatter, not stdlib.)

### 3. On-demand map views — python groundwork landed, Rust plan

Groundwork (landed): `ehp_batch.py sidebyside -` reads the JSONL manifest
from stdin — a single-view job needs no temp manifest file. Measured: one
view renders in ~0.05s; a cold one-shot process (interpreter + pandas/jinja
imports) is ~1–3s wall. `run_slices`' dict fast path applies to all modes.

Rust-side plan (ehp_chart.rs — NOT implemented here, owned by another
workstream):

- **`generate_map_sidebyside` first** (independent, immediate win): replace
  its `poetry run python main.py --sidebyside` invocation with
  `batch_cmd(seqsee_dir)` + `sidebyside -`, piping the single manifest line
  (same JSON shape as `pregenerate_mapviews` emits) to stdin. Kills the
  per-`mapview` poetry startup and uses the resolved venv python;
  `annotate_json_with_jmap` and `post_process_mapview` unchanged.
- **`EHP_MAPVIEWS` becomes tri-state**: `0` = off (unchanged), `all` =
  today's synchronous pre-generation, default flips to `background`:
  startup SKIPS the synchronous `pregenerate_mapviews` block (the
  `want_mapviews` branch after startup generation) and instead spawns ONE
  background thread that runs the existing per-page
  `pregenerate_mapviews` + `refresh_mapview_nav` + `inject_map_info`
  refresh, then prints a completion line. Startup stops paying the
  maps × spheres × pages multiplier (133 views/4.6s at t=25; the dominant
  count at t=100); the tail fills in while the user works. NB the chart
  state stamp embeds `mapviews={bool}` — fold the new mode in so `all` and
  `background` share a stamp value once views are complete (or archive only
  after the background fill finishes; simplest: stamp on completion).
- **e/h/p key fallback flow**: unchanged JS already handles missing files
  (`entry.view` null -> `copyMapCmd('mapview …')`); with `background` the
  window where that fires shrinks to the first minutes. Optional polish:
  the copied-command status message can say "generating in background —
  reload shortly" when mode=background (MAP_INFO gains a `pending` flag).
- **Regen hooks**: mutation-time `regen_affected_charts` regenerates
  sphere/stem/fiber charts but NOT map views (they go stale today, silently
  — `mapview all` is the manual refresh). Add: for each affected sphere n
  on page r, enqueue the (kind, n, tgt, r) jobs whose `map_*.html` exists
  to the background generator (or, minimal version: delete the stale
  `map_*` HTML + `_src.json` so navigation falls back to the on-demand
  copy-command flow instead of showing stale data). Same hook after
  `interpage`/`outside retry` cascades (they funnel through
  regen_affected_charts already).
- **Snapshots/archive**: no format change — the charts-dir clone simply
  contains whichever views exist; missing ones regenerate on demand after
  restore. `snapshot save` during an unfinished background fill just saves
  fewer map views.
